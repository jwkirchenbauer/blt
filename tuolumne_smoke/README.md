## Native generation latency and recomputation

The native timing numbers above describe different cache and warm-up states,
not conflicting estimates of steady-state throughput:

| Regime | What is included | Observed 7B result |
| --- | --- | --- |
| Cold Hugging Face cache | Network transfer, checkpoint materialization, model loading, first-use compilation, and generation | 276.16 s to load, then 43.15 s for the first 16 generated bytes |
| Warm Hugging Face cache | Local checkpoint materialization and model loading, followed by first-use compilation and generation | 166.29 s to load, then 27.00 s for the first 16 generated bytes |
| Hot, model-resident process | Model already on the GPU, allocator initialized, and relevant PyTorch/FlexAttention kernels already compiled by a previous generation | 0.792 s for 16 generated bytes, or approximately 20.2 generated bytes/s |

The hot measurement is the relevant one for repeatedly running the generation
cell in the notebook. The 20.134 GiB peak allocation is almost entirely the
resident model and working memory; it does not imply that native generation
has acquired an incremental KV cache. Likewise, a warm Hugging Face filesystem
cache avoids downloading weights but does not warm GPU kernels. The first
generation in each newly launched Python process can therefore remain much
slower than subsequent generations.

### What is recomputed

The released native entry point is explicitly
[`generate_nocache`](../bytelatent/generate_blt.py#L77). For every output byte
it slices out the complete prefix, recomputes patch lengths, and calls BLT on
that complete prefix:

```python
for curr_pos in range(start_pos, end_pos):
    current_tokens = tokens[:, :curr_pos]
    patch_lengths, _ = patcher.patch(
        current_tokens, include_next_token=True
    )
    logits = model(
        current_tokens, patch_lengths=patch_lengths
    )[:, -1]
```

Consequently, generating byte `x_t` reruns the following chain over the prefix
`x_<t`:

1. The entropy model scores the complete prefix and reconstructs its patch
   boundaries. `realtime_patching=True` means that patching happens online
   during generation; it does not mean that the entropy model is advanced
   incrementally.
2. Patch IDs, encoder and decoder cross-attention masks, and byte-group hash
   embeddings are reconstructed.
3. The local encoder is run over all prior byte positions and all patch
   representations are reconstructed.
4. The global Transformer is run over every patch produced so far.
5. The local decoder is run over the complete byte prefix, after which only
   its final logit is used.

These operations are visible in
[`ByteLatentTransformer.forward`](../bytelatent/model/blt.py#L890). This is
broader than a missing cache in one attention layer: old attention
projections, MLPs, embeddings, patch aggregation, masks, and entropy-model
work are all repeated.

The repository does contain a generic
[`KVCache`](../bytelatent/generate.py#L112), and base self-attention can update
an attached cache. That machinery targets an ordinary causal Transformer
interface that accepts a new token and its position. The top-level BLT forward
method accepts a complete byte tensor and patch lengths instead. Cache-shaped
arguments on some local/global component methods are not wired through the
full BLT path, so the generic cached generator cannot simply be substituted
for `generate_nocache`.

### Why BLT needs more than a conventional KV cache

Efficient BLT inference needs coordinated incremental state at each level of
the hierarchy:

| Component | State an incremental implementation would retain |
| --- | --- |
| Entropy patcher | Entropy-model KV state, the preceding entropy value, and boundary-threshold state |
| Byte features | A short rolling byte history for the 3--8 byte hash groups |
| Local encoder | Its bounded byte-attention window plus byte states belonging to the current open patch |
| Patch construction | The current patch's accumulated encoder/pooling or cross-attention state |
| Global Transformer | KV state for finalized patches |
| Local decoder | Its bounded byte-level KV state and the relevant global patch representations |

The current open patch is the main BLT-specific complication. A normal
Transformer token has a fixed representation as soon as it is appended. A BLT
patch representation is derived from several bytes and changes while more
bytes are assigned to that patch. A server therefore cannot blindly append a
permanent global K/V entry for the open patch after every byte.

The intended approach is to make cheap local byte steps within a patch and
invoke the expensive global Transformer when a patch boundary finalizes the
preceding patch. At that point one finalized patch representation can be
appended to the global cache. A faithful implementation still has to reproduce
the model's shifted encoder/decoder patch alignment, `include_next_token=True`
semantics, and block-causal cross-attention masks. In particular, the exact
point at which a patch becomes eligible for global processing and which global
patch output conditions the next byte must agree with
[`decoder_patch_ids_from_lengths`](../bytelatent/model/blt.py#L118). Adding
`KVCache` only to the global self-attention would not handle these details.

Conceptually, an incremental generation loop would be:

```text
Prefill the prompt into byte-level state and finalized-patch global state.

For each next byte position:
    advance the cached entropy model and decide whether this is a boundary
    if the preceding patch has just become final:
        finalize its patch representation
        run one new patch through the cached global Transformer
        begin a new open patch
    run one incremental local-decoder byte step
    sample the byte and update the local/open-patch state
```

This is feasible because entropy-threshold patching was explicitly designed
to be incremental. The original paper's “Incremental Patching” condition is
`f_p(x_<i) = f_p(x)_<i`: once a boundary has been assigned in a prefix, a
future continuation does not change it. Finalized patch representations and
their global K/V entries therefore need not be invalidated. The global model
remains an ordinary causal Transformer over finalized patches, local attention
has a fixed window, and the hash embeddings need only a short byte history.
There is no apparent architectural requirement to rerun the complete prefix.

There are nevertheless real serving complications beyond cache plumbing.
Different sequences in a batch reach patch boundaries on different byte
steps. Some sequences need a relatively expensive global-patch update while
others need only a local byte step, creating ragged execution and potential
GPU under-utilization. Variable patch lengths also complicate stable shapes,
cross-attention masks, compilation, and paged-cache management. A
high-throughput server would likely need to schedule or bucket local-byte and
global-patch work separately.

### Scaling implications

Kernel warm-up explains the large difference between the first and hot
16-byte generations, but it does not remove the algorithmic recomputation.
As the prompt or generated continuation grows, each native no-cache iteration
processes more bytes and generally more patches:

- Byte embeddings, local layers, and patch construction repeatedly revisit
  the prefix.
- Global MLP work repeatedly revisits every existing patch.
- A full global self-attention pass revisits every patch pair; for sufficiently
  long generation this is substantially worse than one cached query attending
  to prior patch keys.

For short continuations, large fixed overheads and highly optimized hot kernels
can make approximately 20 bytes/s quite usable interactively. It should not be
interpreted as the architecture's optimized serving ceiling, nor should it be
expected to remain constant at long context lengths. A true incremental BLT
path would prefill once, perform one bounded local step per generated byte, and
perform one cached global step only at patch boundaries. That is the serving
implementation required to realize the paper's inference-FLOP motivation.

The four JSONL shards are deliberately tiny fixtures, not training data for a
meaningful model. The successful tests used raw JSONL, space patching, bf16,
xFormers local/global attention, FlexAttention cross-attention, optimizer
steps, exact resume, FSDP checkpointing, consolidation, and strict reload.

On this ROCm stack, native single-prompt, batched, and replicated multi-rank
generation now work with eager BlockMask metadata construction. The converted
`itazap/blt-1b-hf` Transformers path is also available as an independent
pretrained generation route.

## Testing debrief

The main issues fell into three groups: BLT correctness/compatibility bugs
fixed in this branch, ROCm/environment mismatches handled by the installer,
and native-generation faults traced to a deprecated PyTorch compilation path.

| Issue | What happened | Status |
| --- | --- | --- |
| CUDA-specific xFormers assumptions | BLT unconditionally referenced Flash/CUTLASS operators absent from the ROCm xFormers wheel, so importing the distributed code could fail before execution. | Fixed by registering only operators exposed by the installed backend and recognizing the ROCm CK operator in `bytelatent/distributed.py`. |
| Raw JSONL checkpoint resume | Training saved a valid checkpoint, but exact continuation reconstructed the input dataset as Arrow regardless of the configured format. Model and optimizer state loaded before iterator restoration failed. | Fixed by preserving `self.file_format` in `bytelatent/data/iterators/arrow_iterator.py`. Exact continuation from step 3 to step 4 then succeeded. |
| Upstream CUDA-oriented environment | The upstream xFormers source pin targets CUDA and was unsuitable for this ROCm stack. Several packages imported by data and Hugging Face paths were missing from upstream requirements. | `install_tuolumne_291_643_blt.sh` uses the ROCm xFormers wheel and adds `jsonlines`, `safetensors`, `hf_xet`, compatible Hub/Transformers packages, and `accelerate`. |
| Native batched generation | Generating several differently sized prompts together caused a ROCm GPU memory-access fault. The original asynchronous traceback misleadingly stopped at `tokens_to_seqlen`; kernel serialization located the fault in Triton's compiled `create_block_mask` metadata kernel for decoder cross-attention. | Fixed by using PyTorch's supported eager BlockMask metadata builder. The mask and FlexAttention computation are unchanged. |
| Native replicated multi-rank generation | With one prompt assigned to each independent rank, three ranks generated successfully while rank 0 appeared to fault during polynomial hashing. Hash stress tests passed on every GPU, while eager BlockMask construction made all four ranks reliable. | Fixed by the same BlockMask change. The old hash frame was delayed asynchronous fault reporting from an earlier compiled cross-mask kernel. |
| Standalone entropy checkpoint access | `facebook/blt-entropy` returned HTTP 403 during the initial test even after access was requested. | Bypassed by loading the entropy checkpoint embedded in `facebook/blt-1b`. |
| Large checkpoint downloads | Downloads could appear hung and leave partial cache content without the Xet transfer backend. | The partial cache was cleaned and `hf_xet` installed; subsequent cached model loading succeeded. |
| Standalone script imports | Running a script by absolute path sets Python's import root to the script directory and produced `ModuleNotFoundError: bytelatent`. | Commands set `PYTHONPATH="$PWD:$PYTHONPATH"` when the driver imports this checkout. |
| Misleading launcher completion | Generated `launch.sh` prints its final completion message after `flux run`, so that message alone does not prove the inner command succeeded. | The launcher remains unchanged. Inspect explicit success markers and tracebacks in the Flux log. |
| Long first-step compilation | The first FlexAttention execution took roughly 30–35 seconds and initially resembled a hang; later tiny-training steps took tens of milliseconds. | Expected compilation warm-up rather than a failure. The shared TorchInductor cache helps subsequent runs. |

The core training path is healthy: single-GPU training, four-GPU FSDP, RCCL,
backward passes, optimizer updates, checkpointing, exact resume,
consolidation, strict reload, entropy-patched likelihood evaluation, and
native pretrained generation all completed successfully.

## Native generation diagnosis

PyTorch 2.9's `create_block_mask` defines `_compile=False` as its supported
default. Its source marks `_compile=True` as a deprecated internal workaround
whose original limitation has been removed. Upstream BLT explicitly requested
that deprecated path for every encoder and decoder cross-attention mask.

With `AMD_SERIALIZE_KERNEL=3`, the variable-prompt failure was attributed to
the generated Triton metadata kernel for a batch-4 decoder mask with
`Q_LEN=24` and `KV_LEN=44`. The original non-serialized stacks stopped later
at whichever operation next synchronized the GPU, explaining the inconsistent
`tokens_to_seqlen` and polynomial-hash frames.

The following checks separate the primitives from the failing integration:

- `f3Nk1xT1KqGB`: all four GPUs passed 50 iterations of sequence-length
  extraction, official hash widths 3–8 against CPU results, and CK xFormers
  block-diagonal local attention at batch sizes 1 and 4.
- `f3Nk6PD23fN7`: the original compiled BlockMask path reproduced the fault on
  a different node and identified the exact Triton `create_block_mask` kernel.
- `f3Nk8tjRrrZu`: eager BlockMask construction generated all four variable
  prompts successfully in one batch.
- `f3NkB9JUUECf`: four independent ranks generated their assigned prompts
  successfully with the same path.
- `f3NkE9xGf2co`: the final source default, without a diagnostic flag,
  reproduced the successful four-prompt batch.
- `f3NkGcLzYEjZ`: a one-step tiny training regression completed its forward
  pass, backward pass, optimizer update, and clean teardown with the final
  source default.

`BLT_COMPILE_BLOCK_MASK=1` restores upstream's legacy metadata compilation
path for controlled comparisons. It should not be enabled for batched native
generation on this ROCm/PyTorch stack.
